# 채팅 모듈 작업 지침

루트 `AGENTS.md`의 Rust/WASM 경계, i18n, community review와 실제 화면 검수 기준을 함께 적용합니다. 파일 줄 수나 과거 구현 설명을 현재 계약으로 삼지 않습니다.

**검색·볼트 답변의 1순위는 발견 범위입니다. 최소선은 Ctrl+F brute-force 전수검색, 지향점은 Google 같은 검색입니다. 새 사이클·루틴을 정할 때 [루트 검색 개선 이정표](../../AGENTS.md#검색-개선-이정표)를 먼저 적용합니다.**

화면의 배치·시각 위계·문구는 [공통 디자인 언어](../../design.md)를 따릅니다. 모델 프롬프트에는 화면 배치 규칙을 넣지 않습니다.

## 검색 개선 사이클의 시작점

- [루트 검색 개선 이정표](../../AGENTS.md#검색-개선-이정표)의 모델 공통 최저선을 적용합니다. Luna·Astra 모두 Ctrl+F로 찾은 관련 원문을 읽고 답할 수 있는 수준 이상이어야 하며, 단순 검색 결과보다 유용한 설명·종합을 제공해야 합니다. 모델별 실제 최종 답변의 핵심 내용·하위 질문 충족·관련 근거 범위를 비교하고, 미실행 모델은 미검증으로 보고합니다.
- 모델별 발전 방향도 [루트 검색 개선 이정표](../../AGENTS.md#검색-개선-이정표)를 따릅니다. Luna에서는 관련 원문을 누락·왜곡 없이 찾아 출처와 함께 충실히 정리하는 하한을, Astra에서는 같은 근거의 사실·관계·조건/예외를 빠짐없이 논리적이고 읽기 쉽게 종합하는 목표를 검증합니다. 성능이 낮을수록 발견·전달 범위를 줄이는 것이 아니라 불확실한 해석을 줄이고 원문에 충실해야 하며, 성능이 높을수록 필요한 근거를 생략한 유창한 요약이 아니라 충실한 이해·구성·설명의 가치를 더해야 합니다. 모델별 실제 표시 답변에서 근거·핵심 내용의 보존과 종합·가독성을 구분해 평가하며, 현재 구현의 달성 여부와 목표를 혼동하지 않습니다.
- 실제 채팅 최종 답변의 기준선을 확인할 때 같은 자료·범위·일치 조건의 Ctrl+F 전수검색 결과도 대조합니다. 전수검색이 찾은 문서·구간이 후보, 원문 검증, dossier, 후속 탐색, 최종 답변 중 어디서 누락되는지 먼저 추적합니다.
- 원래 질의의 후보가 0인 경우, 교차 언어·동의어 확장이 필요한 경우, 다수 문서·구간이 일치하여 상위 k·예산 밖으로 밀리는 경우를 점검합니다. 일치 총계나 선택된 근거 몇 개의 검증 성공만으로 발견 범위가 보장됐다고 판단하지 않습니다.
- 다음 루틴의 우선순위는 발견 누락 해소가 먼저입니다. LLM이 추가 조사할 수 있는 경로·관련 구간·연결 단서의 보존도 확인합니다. 미검증 단서를 확정 근거로 쓰지 않으며, 모든 원문을 한 번에 컨텍스트에 넣도록 요구하지 않습니다.
- 위 항목과 실제 답변 품질의 미검증을 캐시·지연 개선으로 대신하지 않습니다. 이는 목표·검증 계약이며, 문서에 적혔다는 이유로 현재 구현이 지원한다고 보고하지 않습니다.

## 변경 계약

- 프롬프트 수정은 현재 요청의 목표·언어·형식·분량을 우선하고, 도구 조사 후 결과를 완성하게 합니다. 볼트 인덱스 요약은 대표 샘플이며 전체 볼트의 사실이나 실행 지시가 아닙니다.
- Vault Context와 성공한 도구 결과를 출처로 인정합니다. 검색 후보·생성된 요약·저장된 출처 위치는 원문 검증을 대체하지 않습니다. 근거 부족·실패·제한된 검색을 문서 부재로 단정하지 않습니다.
- 설정 화면·채팅 입력·검색 화면은 같은 RAG readiness 스냅샷을 사용합니다. corpus refresh·pending update·indexing이 하나라도 진행 중이면 부분 색인으로 답하지 않고 preparing/indexing으로 표시합니다. indexing 중에는 검색 화면도 pending 응답을 유지합니다.
- dossier는 채택된 인용 목록만 담지 않고 엔진이 계산한 일치 인벤토리를 포함합니다. 인벤토리는 검색 범위 안의 일치 문서 수·근거 구간 수·발생 횟수와 구문 일치 문서 목록이며, 점수·순위가 아니므로 스코어링이나 후보 자르기에 쓰지 않습니다.
- 답변은 집계 수치를 그대로 인용하고, 구문 일치로 확인된 문서만 "직접 인용"으로 서술합니다. 질문이 열거를 요구하면 인벤토리 범위 안의 확인된 문서를 빠짐없이 나열하며, 검토 예산·상위 k개 컷으로 열거 누락을 정당화하지 않습니다. 인벤토리에 없는 문서·수치는 만들어내지 않습니다.
- 목표는 집계를 모델 도구 왕복 없이 한 번의 엔진 실행으로 끝내는 것입니다. 도구 호출은 금지가 아니지만 볼트 근거 확보의 주경로로 쓰지 않고, 엔진 실패·한계 고지와 경계는 기존 계약을 유지합니다.
- 검색 화면과 일반 볼트 질문은 기본 documentScope all로 전체 색인의 lexical 후보를 BM25로 평가하고, hybrid 후보 신호는 검토 범위가 아니라 순위 prior로만 사용합니다. 엔진은 상위 경로만 원문 검증에 보내며 검색 화면은 현재 revision과 색인 quote를 검증하고, 채팅 답변은 채택 문서의 현재 원문을 다시 읽습니다. 후보가 없거나 candidate 초기화·불가용, 일부 facet 후보 실패가 있어도 전체 lexical 평가와 원문 검증 후보 구성을 계속합니다. 검색·랭킹·근거 선별·존재·행 위치·리비전 검증은 엔진이 담당하며 LLM은 검증된 근거로 답합니다. 기본 답변은 dossier를 해석하되, 엔진이 발견한 단서를 바탕으로 필요한 추가 검색·읽기·관계 탐색을 허용합니다. 후속 자료도 현재 원문·출처 검증을 거쳐 근거에 합칩니다. 기본 발견을 모델의 자발적 도구 호출에 떠넘기거나, 새 근거 없이 답변을 무제한 재생성하지 않습니다. 제외·미색인·미검토 문서는 검토 완료로 표현하지 않습니다.
- 답변 전에 채택 문서의 현재 vault 원문을 다시 읽고 revision과 파일 content hash를 확인하며, 원문을 색인과 같은 청킹 규칙으로 나눈 구간에서 quote·절대 행을 Rust로 검증합니다. mtime:size나 hash 하나만으로 색인 사본의 인용을 verified로 승격하지 않으며, 재검증 실패는 해당 근거와 answer plan을 제외한 incomplete 범위로 처리합니다.
- 비교 질문은 Rust가 만든 facet별 후보 검색과 후보 queryIndex의 근거 귀속을 사용합니다. supported facet별 주장과 양쪽 supported 근거가 모두 있는 종합만 허용하며, missing facet을 supported로 승격하거나 근거 없는 직접 비교를 만들지 않습니다.
- facet 검색 실패·미확인은 문서 부재가 아닙니다. answerPlan 계약을 통과하지 못한 답변은 같은 모델로 정확히 1회 교정하고, 다시 실패하거나 answerPlan을 계산할 수 없으면 provider 답변을 게시하지 않고 해당 답변 시도를 검증된 evidence-only로 마칩니다. 후속 조사 허용은 이 교정 한도를 없애거나 검증 실패 답변을 게시해도 된다는 뜻이 아닙니다.
- 엔진이 전달한 근거 구간의 주변 맥락·조건·예외·상충 근거를 해석에 반영하고, 복합 질문의 주장과 문서 간 관계를 출처에 연결합니다. 직접 확인한 사실과 문서의 전제를 연결한 추론을 구분하며, 근거 없는 빈칸을 사전지식으로 채우지 않습니다. BM25·벡터·하이브리드 검색과 도구 호출의 조율은 제품 책임이며 모델의 자발적 호출에만 맡기지 않습니다.
- 엔진 채택·필터 제외·검증 실패·예산 제외·미검토·미색인·읽기 실패를 구분하고 coverage 고지를 보존합니다. 엔진 검증 실패(quote-missing·position-mismatch·revision-mismatch·out-of-scope)는 사유와 함께 제외하며 모델의 관련성 판단으로 표현하지 않습니다. engine-unavailable·indexing은 반환된 content와 검증 citations를 그대로 표시하고 종료하며, 엔진 실패를 우회하는 모델 도구 루프로 대체하지 않습니다. no-evidence·evidence-only도 반환 content·검증 citations와 한계 고지를 보존합니다. 엔진이 발견한 조사 단서가 있다면 일반 볼트 질문에서도 읽기 전용 search/read/list/links/related를 통한 후속 조사를 허용하되, 접근·제외·취소·원문 검증 경계를 지킵니다. 후속 조사에서 근거를 확보하지 못하면 원래의 근거 부족·제한 상태를 유지합니다. evidence-only 표시 본문은 JSON으로 파싱하지 않습니다.
- 엔진 선별·원문 검증·인용 구절 일치와 출처 ID 검사만으로 해석의 정확성이나 모델 공통 최저선의 충족을 입증할 수 없습니다. 이는 검증 수단의 한계이지 Luna·Astra 등 모델에 따라 기본 답변 품질 하한을 낮춰도 된다는 뜻이 아닙니다. 하한 미달은 미완료이며 모델 교체나 추가 도구 호출만을 해결 조건으로 삼지 않습니다. 근거 없는 주장·조건/예외 누락·문서 간 관계 오판은 독립 합성 자료로 확인합니다. 실제 답변 품질은 루트 `AGENTS.md`의 로컬 QA 참조 답안·사용자 표시 답변 e2e 계약으로 검증합니다. 실제 입력·질의 계획·검색 근거·원문 검증 결과·모델에 전달한 dossier·생성 답변·최종 표시 답변의 연결을 확인해, 부족한 답변의 원인을 검색 누락, 검증 실패, 전달 누락, 종합/표시 오류로 구분합니다. 엔진 검색 결과나 provider mock만 확인하고 사용자 답변까지 검증했다고 보고하지 않습니다. 다음 사이클은 현행 최종 답변과 우수 답안의 대조 및 위 시작점의 전수검색 대조를 먼저 수행하고, 변경 후 같은 조건으로 다시 확인합니다. 발견 문서·구간의 누락, 후속 탐색 단서의 보존, 최종 답변 품질을 각각 보고하며 하나의 통과를 다른 항목의 통과로 대신하지 않습니다.
- 발견 범위·근거 정확성이 속도보다 먼저이며, 루트 [검색 개선 이정표](../../AGENTS.md#검색-개선-이정표)와 1,000ms 검색 지연 계약을 함께 따릅니다. 1,000ms 초과 상태에서도 발견 누락을 남겨 둔 채 속도만으로 사이클의 품질 성과를 대신하지 않습니다. 지연 기준 충족 후에는 추가 속도 최적화 대신 필요한 자료의 포괄성, 근거에 충실한 설명, 조건·예외·상충 근거와 문서 간 관계의 정확한 종합을 개선합니다. LLM 라우팅·생성 시간과 최종 답변 도달 시간은 검색 지연과 분리해 기록하며, 답변을 짧게 하거나 필요한 근거를 잘라 속도 목표를 맞추지 않습니다.
- 명시적 외부 MCP를 포함한 mixed 요청에서만 deferAnswer를 사용합니다. MCP 컨텍스트에는 구조화 dossier JSON과 검증 citations를 주입하고 native vault 도구 정의·실행 권한을 제공하지 않습니다. 외부 discovery·승인·재개와 server-only 요청의 경계를 유지합니다. 승인 재개는 현재 정책으로 근거를 재검증하며, 별도 후보 범위가 저장되어 있지 않으면 기본 all 검토를 사용합니다. 질의 계획은 로컬 결정적 계산만 사용하며 번역을 위한 provider 호출을 하지 않습니다.
- 기본값·빠른 프리셋·생성 프롬프트의 한국어와 영어 계약을 함께 검증합니다. 사용자 저장 프롬프트와 세션별 지침은 자동으로 덮어쓰지 않습니다. 도구 호출 형식·JSON 스키마·출처 ID·재개 경계를 보존합니다.

- `view.ts`에 큰 기능을 누적하지 않습니다. UI·호스트 처리는 전용 모듈로 나누고 결정적 파싱·선택·정규화는 Rust/WASM에 둡니다.
- 기본 `ChatMessage` 타입은 `src/llm/providers.ts`에서 가져옵니다. 저장·표시 메타는 기존 `types.ts` 계약을 확인하고 중복 정의하지 않습니다.
- 메시지와 도구 실행을 바꾸면 취소 후 늦게 도착한 결과, 세션 전환, 중복 실행, 스트리밍 종료·오류와 스크롤 동작을 함께 검토합니다.
- 저장 포맷을 바꾸면 legacy load와 최신 형식의 round-trip을 테스트합니다. 실제 사용자 세션을 테스트를 위해 덮어쓰지 않습니다.
- DOM은 Obsidian API와 `ownerDocument`를 사용합니다. 사용자·모델 출력을 `innerHTML`로 넣지 않고, `.style.*` 직접 대입이나 인라인 스타일을 새로 추가하지 않습니다.
- UI를 바꾸면 관련 구조 테스트·i18n·채팅 UX·community review를 통과시키고, 정상·빈 상태·오류·진행 중·좁은 폭을 실제 스크린샷으로 확인합니다.
