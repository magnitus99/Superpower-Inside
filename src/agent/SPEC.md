# 볼트 근거 심사와 답변 계약

## 책임과 의도

공통 검색 입력에서 후보를 수집하고 원문을 검증해 답변용 dossier와 출처를 만든다. 기본 조사는 모델이 검색 도구를 자발적으로 고를 때까지 기다리지 않는다. LLM 후속 검색·읽기·연결 탐색은 엔진이 발견한 단서를 깊게 조사하는 수단이며 기본 발견·집계를 대체하지 않는다. 답변 총실도·참조 기준은 아래 절이 소유한다.

엔진의 일치 인벤토리는 문서 수·근거 구간 수·발생 횟수와 구문 일치 문서를 표현한다. 순위나 채택 근거 수와 다르다. 직접 인용은 엔진 구문 판정으로만 서술하며 열거 질문에서는 확인된 문서를 예산을 이유로 생략하지 않는 것이 요구 계약이다.

## 근거 자격과 실패 경계

채팅에 채택할 문서는 현재 본문을 다시 읽고 revision·파일 content hash를 확인하며 같은 청킹 규칙의 구절·절대 행을 Rust로 검증하는 것이 요구 계약이다. mtime:size나 hash 하나만으로 색인 사본을 verified로 승격하지 않으며 재검증 실패는 해당 근거·answerPlan을 제외한 incomplete로 처리한다. 아래 현재 차이를 함께 적용한다. 색인 후보, 인벤토리, 저장된 주소와 현재 원문 검증 출처를 구분한다. 읽기 전후 stat·파일 identity 검사는 변경 감지 보호 장치이며 그 자체가 quote 검증은 아니다. 현재 reader가 hash를 생략하면 같은 호출이 읽은 전체 원문에서 문서당 한 번 계산한다. 계산할 수 없으면 그 문서는 미검토로 남긴다. 일반 검증·주소 교정·재선택 복구 모두 현재 revision·hash만 채택하며 색인이나 복구 후보의 hash를 상속하지 않는다. 현재 청크는 인용 가능 범위만 제한하고, 선택 구절과 절대 행은 현재 전체 추출 본문에서 자른 행 창으로 Rust가 확인한다. 기존 주소가 틀리면 현재 전체 본문에서만 교정 후보를 얻는다. 큰 파일은 전체를 행 배열이나 WASM JSON으로 복제하지 않고, 원문 문자열에서 겹친 출현까지 포함해 단 한 곳에서 찾은 완전한 인용만 위치 힌트로 쓴다. 희소한 절대 행 오프셋과 제한된 현재 본문 창으로 Rust가 주소를 제안하고 현재 revision·범위·구절·교정 행을 다시 검증한다. 교정 좌표로 인라인 ID와 저장 인용을 함께 만든다. 창에만 있는 일치나 청크끼리의 일치는 증명이 아니다. 구절 단위로 검증하므로 큰 파일의 무관한 청크나 같은 파일의 실패한 형제 구절이 검증된 인용을 지우지 않는다. 실패한 구절은 미완료로 남긴다.

필터 제외·검증 실패·예산 밖·미검토·미색인·읽기 실패를 자료 부재나 모델의 관련성 판단으로 바꾸지 않는다. 하드 제외 자료는 후보·점수·집계의 세계 밖에 두고 검색 결과에서 그 존재를 노출하지 않는 것이 정책이다. 검색 내 미검토 자료와 하드 제외를 혼동하지 않는다. 검색 수집은 serving 색인 경로와 요청에서 얻은 현재 정책·명시 스코프의 교집합을 BM25 batch, 개별 fallback, 로컬 변형과 term 집계에 똑같이 넘긴다. 제외 경로는 원문 심사에서 뒤늦게 거르는 대상이 아니라 raw discovery에도 들어오지 않는다. 원문 심사와 후속 페이지의 현재 접근 정책 재확인은 별도로 유지한다.

indexing·engine-unavailable·no-evidence·evidence-only를 구분하고 반환된 한계와 검증 출처를 유지한다. answerPlan 형식 실패는 같은 제공자의 같은 모델로 한 번만 교정하며 다시 실패하거나 answerPlan을 계산할 수 없으면 그 답변 시도를 검증된 evidence-only로 끝낸다. 외부 결과나 관련성 판단만으로 실패한 인용을 verified로 승격하지 않는다. 후속 조사에도 현재 정책·원문 검증·실행 취소 경계를 적용한다. 계획 모델은 접근이 확인된 첫 단서 페이지의 주소와 전체 집계만 받고 미검증 색인 본문은 받지 않는다. 나머지 단서는 로컬에서 후속 검색 범위를 유지하며, 선택적 후속 계획·검색은 12초 제한에 도달하면 이미 시작한 corpus I/O가 취소 신호를 받지 않아도 기본 검토로 돌아간다. 늦은 결과를 병합하거나 그 검색의 다음 읽기를 시작하지 않는다. 사용자 취소는 제한 만료와 달리 검토 자체를 중단한다. 최종 생성·교정 직전에 소유권과 적용된 literal 원장의 유효성을 다시 확인한다. 현재 검증한 인용과 주소만 전달하고 미검증 인접 색인 문맥과 큰 원장은 복제하지 않는다. 교정 예산에서 필수 dossier가 빠지면 이전 응답을 제외하고 다시 예산화하며 dossier 없이 발송하지 않는다.

## 전달·비교·후속 조사 요구

기본 documentScope all에서 접근 가능한 전체 색인의 lexical 후보를 BM25로 평가한다. hybrid 후보는 순위 prior이며 검토 세계를 제한하지 않는다. 후보 초기화 불가·빈 후보·일부 facet 실패여도 전체 lexical 평가와 원문 검증 후보 구성을 계속한다. 기본 발견·집계·구문 판정·구간 주소는 모델 도구 왕복 없이 엔진 한 번·색인 한 순회에서 확보하는 것이 목표다.

`matchInventory`의 BM25 exact-token/구문 집계와 `literalInventory`의 원문 부분문자열 문서·행·발생은 별도 단위로 표시한다. literal 정의는 `deterministic-core`, 저장·currentness·lease는 `retrieval-index`가 소유한다. 직접 literal 입력을 planner term보다 먼저 보존하고 Rust가 계산한 총계를 전달한다. literal 실패·미지원 필터를 token 숫자나 성공 0으로 대체하지 않으며 해당 상태를 모델 전달 전부터 명시한다. 모델에는 일치 정의·범위·숫자를 전달하고 내부 receipt/세대 ID는 복제하지 않는다.

조사는 전체 literal 원장의 처음 최대 8페이지에서 위치 힌트를 읽고 그 힌트 자체를 Rust 대표 계획에 넣어 기존 검토 경로와 합친다. 기존 discovery 기록이 새 힌트의 대표 슬롯을 소비하지 않으며 기존 후보의 순위 prior를 같은 위치 일치로 중복 강화하지 않는다. 새로 발견한 경로는 bounded discovery 후속 심사를 먼저 받을 수 있고, 색인에서 읽었지만 근거로 선택하지 않은 새 literal 경로를 현재 원문 심사 완료로 간주하지 않는다. 이 한도는 전체 원장 총계나 후속 비동기 페이지를 자르지 않으며, 읽은 페이지·선택한 경로·현재 원문 심사는 별개다. reference는 인용이 아니므로 새 단서도 같은 원문 검증을 통과해야 한다. source 요청은 lazy opener로 얻은 handle을 소유하고 모델/후속 소비와 비동기 페이지 정리가 끝날 때까지 실제 serving lease를 유지한다. 결과의 페이지 callback은 그 요청 수명 안에서만 유효하며 종료는 await한다. literal 유효성을 마지막으로 재확인한 뒤에도 원래 요청 signal과 조사 실행 소유권을 다시 확인하며, 그 전에 최종 답변·완료 callback을 게시하지 않는다.

인벤토리는 점수·후보 컷에 쓰지 않고 수치를 그대로 전달한다. 비교는 Rust facet 계획과 후보 queryIndex 귀속을 사용하며 supported facet의 주장과 양쪽 supported 근거가 있는 종합만 허용한다. missing facet을 supported로 바꾸거나 근거 없는 직접 비교를 만들지 않는다. 주변 맥락·조건·예외·상충 근거를 보존하고 확인 사실과 문서 전제에 근거한 추론을 구분한다. 생성과 1회 교정 모두 하위 질문별로 확인한 답을 유지하고, 같은 출처가 지지하는 주장끼리 문단을 구성하며, 확인하지 못한 항목만 한계로 표시한다. 모델용 근거의 `facetIds`는 기존 answerPlan의 supported facet `sourceIds`를 역으로 투영한 것으로, 검색 번호를 재해석하거나 facet 지지 여부·출처 키·검증 판정을 바꾸지 않는다. 귀속되지 않은 검증 구절은 실제로 지지하는 보충 설명에만 쓰며 facet 필수 근거를 대신하지 않는다.

후속 발견 후보나 원래 범위가 비면 후속 계획·심사를 위해 전 볼트 경로를 재조회하지 않는다. 비교의 미검토 facet 단서가 있으면 먼저 기본·후속 병합 결과의 Rust facet별 출처 중 현재 원문을 통과한 구절이 있는지 확인한다. 빈 항목의 `queryIndex` 단서를 먼저 읽고, 전체 질문을 다시 채점하지 않고 그 항목의 질의·핵심 term 변형으로 구절을 고른다. 부족한 항목이 여럿이면 각각 독립 검색으로 평가한다. 발견 원장과 8페이지·8경로 제한은 유지하며, 독립 검색의 번호나 경로 순위를 귀속으로 상속하지 않는다. 선택 구절이 해당 항목의 모든 term을 담고 현재 원문 재검증도 통과해야 새 지지 출처가 된다. 사전 검증은 순서만 결정하며, 비동기 조사 뒤 최종 근거는 정책과 원문을 다시 확인한다. 그 뒤 현재 원문 재검증·재선택에도 빠진 항목은, 필터 없는 요청에서 현재 정책 재조회가 가능할 때에만 이미 corpus가 정상 조사한 경로 최대 8개에서 해당 항목 질의와 엔진 term 변형을 독립적으로 평가한다. 현재 청크 범위의 실제 행을 쓰며 경로 prior나 부분 단어 일치는 새 facet 귀속이 아니다. 청크·행의 후보 힌트와 최종 구절 판정에 계획과 같은 단어 경계(NFKC, 소문자, 영숫자와 `-`·`_`)를 적용하며, BM25의 부분 토큰은 사용하지 않는다. 새 귀속에는 선택 구절 자체의 전체 facet term coverage, 현재 본문·청크 검증, 읽기 뒤 허용 경로 재확인이 필요하다. 실패하면 미지지를 유지한다. 이러한 lexical 귀속이 의미 충실도나 비교 결론의 증명은 아니다.

선택된 채팅 모델의 기존 후속 계획 1회에서 질문·허용된 주소 페이지·본문 문자권별 개수만으로 대상 표현과 원문 언어 검색어를 제안할 수 있다. 비교 대상은 원 질문에 있는 어절 구간으로 제한하고, 표기가 달라도 정규화 후 같은 구간에 매칭된 경우 양쪽 대상으로 인정하지 않는다. 짧은 identity와 주변 검색 단어를 구분한다. 각 쪽의 완전한 번역 식별 구문과 길이 기준을 충족하는 질문의 원표기 구문을 같은 쪽의 대안으로 현재 허용 serving BM25에서 검색한다. 검색·인용 identity의 길이 기준에 못 미치는 원표기도 양쪽의 충돌 검사에는 반드시 포함한다. 정규화한 어느 대안 쌍에서든 한쪽의 전체 식별 단어가 반대쪽 대안에 포함되면 뒤바뀜·겹침으로 거절하고 기본 비교 계획을 유지한다. 문맥 질의는 짧은 목록의 구절 순위에 쓰고 식별 증명에는 쓰지 않는다. 각 쪽 상위 경로를 독립 순위화하고 번갈아 최대 8경로를 같은 제한된 원문 심사에 넘긴다. 현재 허용되는 순위 경로가 없으면 기본 발견 심사를 그대로 실행하고, 일부만 있으면 기존 발견 페이지에서 중복 없이 남은 슬롯을 채워 원래 질의·후보 계약으로 별도 심사한다. 두 경로 선택은 합계 8경로·발견 페이지 최대 8장으로 제한되고 기존 인용 예산을 공유한다. 순위 경로 심사 뒤 기본 발견 경로를 읽기 직전에도 접근을 다시 확인하며, 기본 발견 경로는 새 facet 번호를 상속하지 않는다. 전체 질의를 다시 코퍼스 전체에 대입하지 않는다. 12초 기한은 모델 계획과 BM25 재발견까지이며 이후 이미 존재하는 최대 8경로 심사를 쓴다. 순위 결과만으로 기본 계획이나 귀속을 변경하지 않는다. 기본 재선택과 누락 항목 탐색을 마친 뒤, 병합에 남아 현재 원문 검증을 통과한 새 순위 구절이 재해석을 직접 지원하고 기존 지원 항목과 종합 가능성을 모두 보존할 때만 새 계획을 채택한다. 대상 재해석 시 이전 번호·경로 귀속을 끊고 적어도 한 완전한 식별 표현의 모든 단어가 선택 구절 안에서 일치하고(한글은 명시한 조사만 허용), 현재 원문 증명이 있는 경우만 새 귀속으로 쓴다. 순위화가 식별 표현을 잘라냈으면 순위 구절을 실제 포함한 제한된 현재 행 창에 한해 인용 후보를 다시 만들고 같은 verifier로 재검증한다. ngram·순위·번역 제안은 지지가 아니다. 질의/identity의 의미 동등성은 개수로 입증되지 않는다. engine-only·모델·제외·범위·선택적 후속 호출 한도는 바뀌지 않는다.

검증한 구절의 바로 앞·뒤 현재 행은 원래 근거를 대체하지 않는 보충 인용이다. 원문과 현재 청크에서 같은 인용·절대 행을 검증하며, 구조 구간이 있으면 그 경계를 넘지 않는다. 이미 전달한 행과 같은 텍스트를 반복하지 않고 최대 8행·합계 UTF-8 4096바이트·전체 64개 이내에만 추가한다. 인접은 조건·반례의 의미 판정이 아니다. `adjacentTo`는 인접 관계일 뿐 `answerPlan` 지지를 만들지 않으며, 첫 전송의 예산에 맞지 않으면 필수 원래 dossier만 재준비한다.

`indexedReviewDiagnostics.stageTrace`는 그 턴의 일곱 관측 단계에 대응한다. 개발용 추적에서는 같은 값을 `review.stageTrace`로 제공한다. 질의문, 본문, 파일 경로는 남기지 않는다. 대신 facet 번호와 개수, 예산, 현재 원문 검사의 첫 거절 사유별 구절 수, 서로 다른 인용 텍스트 수, 검증된 답변이 인용한 0부터의 dossier 번호를 남긴다. 처음 거절된 구절이 재선택 뒤에도 제외됐다는 뜻은 아니다. 선택적 후속 실패는 정책 조회·페이지·예산·모델·계획·범위 재확인·검색·병합 중 관측된 단계와 제한 만료를 구별한다. 그 후에도 비교 쪽이 비면 제한된 현재 원문 독립 탐색의 진입·완료 여부, 청크 부재, 용어 창·순위화·전체 용어 충족 수와 현재성·정책 제외 수를 남긴다. 이 집계는 그 탐색 범위만 설명하며 볼트 전체에 자료가 없다는 증명이 아니다. 구성을 끝낸 dossier가 제공자에게 전달됐는지는 발송 관측에서 따로 확인한다. `displayAndCitations`의 엔진 값은 null이다. 표시는 실제 재열기로 검사하며 숫자만으로 의미 합격이나 최초 의미 손실을 결정하지 않는다. 최종 결과 종류는 진행 사본에도 전달하되 일반 기록의 저장 범위와 배포판 추적 설정은 바꾸지 않는다.

생성·교정 dossier의 `paragraphContract`는 검증 근거 ID와 supported facet ID만 각 배열의 선택지로 제시한다. `allowedSourcesByFacet`는 실제 허용 출처를 제시한다. 단일 항목은 원래의 source ID 문단 형식을 유지한다. 비교 항목에만 별도로 주 지지 쌍 `supportChoices`와 `additional`로만 고를 `supplementalChoices` 및 해당 형식의 예시 하나를 제공한다. 모델은 각 주장에 대해 해당 쌍을 명시적으로 고른다. 별칭은 해당 전송 내에서만 사용하고, 선택한 쌍만 원래 주소·facet으로 역변환하여 동일한 Rust 문단·출처·양측/종합 validator에 넘긴다. 미선택 쌍을 보충하지 않으며 양식을 혼용하거나 알 수 없는 키는 보정하지 않는다. 귀속 없는 인접 근거는 다른 지지 쌍을 보충할 수 있을 뿐이다. 동일 텍스트는 첫 인용을 `sameQuoteAs`로 참조해도 각 행의 원래 출처·조건·주소·귀속은 유지한다. 예시는 문단 형태이지 사용해야 할 근거나 전체 답변의 길이가 아니다. 템플릿의 표시 형식이 문단 JSON 계약을 대체하지 않는다. 교정에는 validator의 고정 field 사유를 전달하며 모델 출력을 진단 로그로 복제하지 않는다.

quote-missing·position-mismatch·revision-mismatch·out-of-scope는 엔진 검증 사유로 제외하며 모델의 관련성 판단으로 표현하지 않는다. engine-unavailable·indexing은 반환 content·검증 citations로 종료하고 엔진 실패를 우회하는 모델 도구 루프로 대체하지 않는다. no-evidence·evidence-only도 한계를 보존하며 evidence-only 표시 본문을 JSON으로 재해석하지 않는다.

단서 기반 읽기 전용 search/read/list/links/related와 전체 열거에도 현재 접근·제외·필터·revision·원문 검증·취소를 적용한다. 후속 근거가 없으면 원래 제한 상태를 유지하며 추가 조사 허용이 교정 한도를 없애거나 검증 실패 답변을 게시할 권한은 아니다. 실제 최종 답변의 의미 충실도는 형식 검증과 별개다.

품질 평가의 `executionMode: 'engine-only'`는 같은 발견·현재 원문 심사·dossier 경로에서 후속 모델과 답변 생성을 금지한다. `deferAnswer`만으로 이 경계를 대신하지 않는다. 전용 serving-only lexical lease가 없으면 평가를 차단하며 일반 검색 포트·초기화·제공자·별도 기준선으로 우회하지 않는다. 이 평가의 단위 통과는 실제 모델 답변의 충실도 합격이 아니다.

발견·검증·판정의 기본 주체는 결정적 검색 엔진이다. LLM은 엔진이 확보한 근거를 해석·종합하며 후보 선별자나 근거 검증자로 대체되지 않는다. 도구 호출은 엔진의 기본 결과가 부족할 때 조사를 깊게 하는 수단이며 기본 발견·검증을 대신하는 경로가 아니다.

확신도가 낮은 후보를 잘라 버리지 않는다. 확신도와 대안 해석을 함께 제시하고 확신이 높은 근거를 먼저 보여 주며, 확인한 범위와 의도한 자료가 다를 수 있음을 사용자가 확인할 수 있게 한다. 맥락이 다르다는 이유로 전부 제외하는 것과 확인을 요청하는 것은 다른 결과다.

## 답변 총실도와 참조 기준

볼트 답변의 참조 기준은 로컬에 보관한 사용자 제공 우수 답안이다. 원문·질의·문서명·답변은 공유 명세·fixture·기억에 복제하지 않는다. 같은 자료·질문·범위에서 색인 범위의 일치 문서 수·근거 구간 수·발생 횟수를 제시하고, 모든 주장에 문서·구간 주소를 연결하며, 직접 인용은 엔진 구문 판정으로만 서술하고, 열거 요청은 확인된 문서를 빠뜨리지 않고 전달한다. 아주 긴 열거는 묶음 요약과 추가 제공 제안으로 표시할 수 있으나 확인된 집합을 줄이거나 누락을 요약으로 숨기지 않는다. 예산·상위 k로 열거 누락을 정당화하거나 제품 실패를 자료 부족으로 설명하지 않는다.

발견과 표시·검증 예산은 다르다. 전체 점수화·일치 총계가 전체 발견 결과의 보존을 뜻하지 않는다. 상위 근거만 현재 원문 검증·답변 컨텍스트에 넣더라도 나머지 경로·관련 구간·연결 단서를 추적하고 후속 조회할 수 있어야 하며, 모든 원문을 한 번에 모델에 넣으라는 뜻은 아니다.

모델 공통 하한은 대상 모델별 실제 표시 답변에서 확인한다. 실행하지 않은 모델은 미검증이고 다른 모델의 통과로 대신하지 않는다. 발견 범위·근거 정확성·최종 답변 총실도를 각각 판정하며, 인용 형식·테스트·mock·오프라인 계약·선택 근거 및 개의 성공으로 해석 정확성이나 전체 recall을 증명하지 않는다.

검색 개선은 같은 질문·자료·모델·설정의 실제 최종 표시 답변을 참조 답안·전수검색과 대조하는 것부터 시작한다. 전수검색 기준 → 엔진 발견 → 후보 보존 → 현재 원문 검증 → dossier 전달·후속 탐색 → 최종 답변 중 최초 손실을 나누고 발견 누락을 먼저 고친다. 합성 회귀는 실제 자료 평가를 대신하지 않는다.

## 현재 구현과 목표의 차이

- `src/search/indexed-search-deps.ts`는 exhaustive lexical 후보와 discovery 단서를 보유하면서 원문 심사 경로를 최대 96개로 선택한다. 따라서 전체 lexical 발견을 전체 현재 원문 검토 완료로 해석할 수 없다. `indexed-vault-review.ts`의 coverage는 이제 원문을 실제로 읽은 경로만 `reviewedDocuments`로 세고, 발견 범위는 discovery 단서·일치 인벤토리·후속 조회로 분리한다. 검토 예산 밖 경로를 미검토 실패로 부풀리지 않지만, 발견 범위와 원문 검증 범위가 다르다는 사실은 그대로다.
- 검토 예산 밖 discovery 페이지는 후속 질의 뒤 `unreviewed` 상태의 고유 경로를 최대 8개(discovery 페이지 최대 8장) 골라 같은 질문·로컬 질의 변형·원래 후보의 facet 귀속으로 한 번 더 검색하고, Rust 현재 원문 검증을 통과한 근거만 dossier에 합칩니다. 필터가 있으면 현재 정책 재조회(`getFollowupPaths`)가 있을 때만 실행하며, 재조회·추가 검색 실패나 취소는 기존 검증 근거를 유지합니다. 이 자동 조사는 발견 전체를 다시 검토하는 장치가 아니며, 8경로·8페이지 밖의 단서와 실제 답변 품질·전체 recall은 이 경계의 검증 대상이 아닙니다. 현재 원문이 바뀐 discovery 근거의 복구도 원래 후보를 유지하고 확장 예산으로 재병합해 기존 검증 근거를 고정 상한으로 자르지 않으며, 병합에서 제외된 구간은 진단과 미완료 고지에 반영합니다.
- 기본 생성에는 인벤토리 총계가 전달되고, 목록·개수 의도는 후속 모델 응답과 무관하게 Rust 결정적 감지로 `enumerate` 경로를 실행한다. 최종 모델 답변이 없더라도 현재 검증을 마친 목록과 인용을 표시한다. 다만 일치 인벤토리가 상한으로 자른 문서는 `missing`으로 남으므로 전체 무누락은 인벤토리 범위에 한정된다. 관련 근거는 `indexed-vault-followup.ts`, `indexed-vault-enumeration.ts`와 `indexed-vault-review.test.ts`다.
- 채팅 검증은 현재 본문을 읽고 구절·절대 행 주소를 Rust로 재검증하며, 현재 파일 content hash를 색인 hash와 비교해 다르면 현재 revision·hash로 갱신한다. 해시 일치만으로 색인 사본을 verified로 승격하지 않는다. 제품 검색 포트도 `forceRefresh: true`·`verifyCurrentSource: true`로 현재 본문·좌표를 검증한다. reader나 명시된 청킹 결과가 없으면 실패 폐쇄하며, 명시적인 legacy `false`는 제품 포트가 사용하지 않는다. serving snapshot의 null은 building corpus나 이전 원장으로 대체하지 않는다.
- 기본 발견·집계·주소를 엔진 한 번·색인 한 순회에서 얻는 것이 목표다. BM25 facet 검색과 term 집계는 term 128개·입력 상한 안에서 `Bm25RuntimeIndex.batch_search_and_aggregate_json` 한 번의 worker 호출로 합치고 선택 chunk의 원문 주소도 한 번에 읽는다. 상한을 넘거나 batch가 실패하면 같은 허용 집합으로 facet별 대표 경로 검색·term 집계를 수행한다. 개별 검색도 Rust에서 대표 경로를 한 번에 선별하므로 상위 청크 범위를 반복해 넓히지 않는다. 기본 검색 변형은 로컬 질문 분해를 사용하고, 일반 채팅의 제한된 후속 발견은 위 선택 모델·지역 BM25 계약을 사용한다. 다만 vector 후보 임베딩·검색은 facet별 호출이 남아 있어 전체 발견 경로의 단일 순회는 아직 아니다.

구현 중심은 `indexed-vault-review.ts`의 `searchIndexedVault`·`reviewIndexedVault`다. `research-agent.ts`는 의도 분류와 진행 라벨만 제공하며 실행 에이전트를 포함하지 않는다. 회귀 근거는 `indexed-vault-review.test.ts`, `indexed-vault-search.test.ts`, `indexed-vault-followup.test.ts`, `src/search/indexed-search-deps.test.ts`, `src/search/engine-adapter.test.ts`다. 로컬 회귀 계약과 실제 답변·전체 recall 검증은 별개이며, 이번 편입에서는 실제 답변·전체 recall을 재측정하지 않았다. 달성 상태와 종료 판정은 [engineering-contract.md](../../engineering-contract.md#검증-상태와-이력)의 검증 상태 절이 소유한다.

## 단일 순회 통합 설계(미구현)

**호출 수 기준선.** 정상 실행에서 한 검색 계획은 `MAX_HYBRID_FACETS`(3)개까지의 facet에 대해 `src/search/indexed-search-deps.ts`의 `querySemanticCandidates`를 facet마다 호출한다. facet마다 원 질의로 `engine.query`를 1회 호출하고, 질의가 24자 이상이며 필터·중복 제거 후 term이 2개 이상이고 압축 결과가 원 질의와 다르면 1회를 더 호출한다. 따라서 facet이 있는 계획의 정상 경로는 엔진 호출 1~6회다. 이는 실제 vector 검색·색인 순회·제공자 요청 횟수 계측이 아니다. 임베딩 사용 불가·쿨다운·이전 실패이면 임베딩을 생략하고, timeout·실패로 질의 벡터를 얻지 못해도 vector·ANN provider는 건너뛴다. 이 경로는 BM25를 제외해 호출하므로 lexical 후보 보존은 별도로 병렬 실행하는 BM25 경로와 구분한다. 회귀 기준선은 `src/search/indexed-search-deps.test.ts`의 "다중 facet 계획은 엔진 질의를 facet마다 따로 보낸다"(mock 엔진 호출 3회)와 긴 질문의 원문·압축 질의 2회 테스트다. 4개 이상 facet의 절단은 아직 테스트로 고정하지 않았다.

**목표.** 계획 1회당 vector 질의 batch 1회와 임베딩 batch 1회로 줄이고, 후보는 facet별 `queryIndex` 귀속과 현재 순위 prior를 그대로 유지한다. 채팅 실행은 변형 계획을 최대 3개 더 돌리므로 계획당 batch가 끝나도 실행 1회에는 계획 수만큼 batch가 남는다.

**설계 후보.** `deterministic-core`가 facet별 질의 목록·결과 귀속 계획을 계산하고, `RAGQueryEngine`이 임베딩·vector worker의 batch I/O를 조율한다. worker는 다중 질의의 결과를 질의 index로 반환한다. 실제 제공자의 batch 지원·요청 수와 worker 호출 수·색인 순회 수·지연은 각각 측정하며 하나의 API 호출이 단일 순회나 성능 향상을 보증하지 않는다. batch 실패·상한 초과 시 기존 facet별 경로를 사용하고, timeout 뒤 fallback은 남은 전체 예산 안에서만 허용한다. 사용자 취소 후에는 재실행하지 않으며 facet별 진단(`semantic:<facetId>`)을 유지한다.

**수용 기준.** 성공 경로에서 batch 엔진 API 호출 1회·개별 `engine.query` 호출 0회를 테스트로 고정하고, fallback 경로에서는 facet별 호출과 `semantic:<facetId>` 진단이 유지되는지 확인한다. batch와 개별 경로의 후보·점수·순위가 같은지 확인하고, WASM 실패를 TS 계산으로 대체하지 않는다. 후보 상한·검토 예산·열거 총실도는 바꾸지 않는다.

**상태.** 미구현이다. 이번 사이클은 mock 기반 엔진 호출 수 특성화와 설계 기록까지이며, 실제 제공자·worker·색인 순회·지연 계측은 하지 않았다. 순위·검토 세계·답변 자격은 이 변경의 대상이 아니다.
