# 수동 제품 철학 검토 양식

**검토 준비용 양식이다. 이 문서를 작성·읽거나 일반 작업을 한다는 이유로 철학 검토를 실행하지 않는다. 사용자가 범위를 지정해 요청할 때만 사용한다.**

이번 정리는 이 양식을 준비하는 단계까지다. 실제 제품 흐름·화면 관찰과 구체적인 수정안 작성은 사용자가 별도 세션에서 진행하기로 했다.

## 필요한 자료만 선택하기

1. [핵심 기준](../../product-philosophy.md)에서 해당 변경의 목적과 적용 원칙을 확인한다.
2. [작업별 탐색표](../02-task-map.md)로 필요한 문서·출처 ID만 고른다. 목록의 원칙은 검토 초점이며 나머지 승인 조건을 무효로 하지 않는다.
3. 근거는 공식 설명·커뮤니티 경험·조사자의 해석·현재 구현·실제 관찰을 구분한다. 사례가 있다는 이유로 우리 동작의 합격을 판정하지 않는다.

## 최소 검토 기록

빈칸을 실제로 확인한 내용으로 채운다. 이 양식은 제품을 검사한 결과가 아니다.

| 항목 | 기록할 내용 |
| --- | --- |
| 범위 | 사용자가 요청한 대상·변경과 필요한 작업 경계 |
| 사용자 목적과 부담 | 완성하려는 일, 현재 관여·반복 작업·시선 이동·맥락 재확인 |
| 적용 원칙 | 승인된 P-ID와 필요한 조건; 근거가 겹치면 추가하지 않은 이유 |
| 전후 흐름 | 어떤 동작이 달라지고 다음 단계에 무엇이 이어지는지 |
| 실제 근거 | 확인한 구현·호출부·테스트·관찰과 출처 ID; 실행하지 않은 것은 미검증으로 표시 |
| 판단과 처리 | 방향에 맞음·어긋남·근거 부족·비해당 중 하나와 이유, 필요하다면 수정 내용 |

단순한 변경은 하나의 흐름으로 기록한다. 복합 변경은 사용자 작업 단위로 나눈다. 내부의 상세 사고 과정이나 변경 없는 모든 단어에 대한 장문 보고서를 요구하지 않는다.

## 대상에 따라 추가할 질문

| 대상 | 필요한 질문 |
| --- | --- |
| 문구 | 왜 지금 보여 주는가? 사용자의 어떤 판단을 돕고 실제 상태와 어떤 관계인가? |
| 버튼 | 왜 이 동작이어야 하는가? 실제 효과·부작용·실패·취소 범위는 이름과 일치하는가? |
| README | 왜 이 글자·단어·문장이 필요한가? 대상 사용층과 약속의 실제 범위에 맞는가? |
| 화면·시선 | 무엇을 찾느라 다시 보는가? 전환 뒤 맥락을 다시 파악하는가? 표현 변화가 읽는 흐름을 끊는가? |
| 자료·계산 | 다음 단계가 활용할 본문·출처·확인 상태가 이어지는가? 제한된 결과를 충분한 처리로 표시하는가? |
| 영상·마케팅 | 전달하는 경험이 실제로 가능한가? 시간 편집·모의 장면·생략한 조건이 약속을 바꾸는가? |

실제 화면·동작 검증은 해당 작업의 AGENTS.md와 design.md를 따른다. 이 양식이 새 레이아웃 규칙·성능 임계값·검색 정책을 만들지는 않는다.

## 변경과 승인의 구분

- 승인된 방향·조건을 그대로 적용하거나 근거·표현을 보완하면 같은 내용을 다시 승인받지 않는다.
- 방향·조건을 바꾸거나 새 조건을 추가한다면 기존 내용·변경 내용·사용자 경험에 미치는 영향을 채팅에서 설명하고 해당 범위만 승인받는다.
- 근거 부족은 통과로 처리하지 않는다. 테스트 통과와 실제 모델 결과 품질·사용 만족은 구분한다.

## 검토와 결과 보고

철학 검토는 ThinkRail 네이티브 위임 도구의 읽기 전용 검토 역할이 맡는다. 과거 역할명이나 Codex 설정을 현재 실행 경로로 사용하지 않는다. 자동 실행 명령·스크립트는 두지 않으며, 사용자가 범위를 지정한 요청과 수정 승인으로만 진행한다. 이 양식 자체가 검토 입력이나 실행 기록을 대체하지 않으며 Patina·TypeScript 구현·품질 검사·Git 훅·CI·릴리스에 연결하지 않는다.

작업 후 사용자에게는 **무엇을 했고 무엇을 고쳤는지 두괄식 불렛포인트**로 요약한다. 철학 작업의 설명 보완과 실제 구현·검증의 결과를 구분한다. 디자인 수정·커밋·릴리스 등 다른 영역은 그 영역의 기존 워크플로우를 따른다.
