# 가치 선언을 제품 동작으로 옮기는 중간 설명

**상세 보조 설명이다.** 현재 기준은 [제품 철학](../../product-philosophy.md), 기본 근거 경로는 [작업별 탐색](../02-task-map.md)이다. 아래 구현 연결과 가상 시나리오는 실제 제품을 검토한 결과나 새 요구사항이 아니다.

**“심플하다”, “보이지 않게 노력한다”, “알아서 한다”는 말만으로 개발 결정을 내릴 수 없다. 어떤 사용자 부담을 제품이 어떤 동작으로 대신 맡고, 다음 단계에 무엇을 남기는지까지 설명해야 한다.** 2026-10-13 사용자는 가치 선언과 제품 예시 사이의 설명이 부족하다고 지적했다. 이 문서는 그 연결을 보완한 설명이다. 이후 P01은 사용자 역할 자체의 자동화를 포함하는 조건으로 승인됐다. P02는 기본 품질 조건으로 승인됐고 P03은 P01의 중복 적용 설명이다. P04는 사용자의 주의를 목적과 결과에 두는 방향으로 승인됐다. P05는 전체 흐름의 편안함으로 발전을 판단하는 기준으로 승인됐고 P06은 P01의 중복 적용 설명이다. P07은 중복 독립 철학에서 제외했고 P08은 기존 계약이다. P09는 사용 과정의 만족을 고객 가치로 승인했다. 초기 후보의 나머지는 선행 기준에 포함되는 적용 설명이다. 새 비교 제품 특성 전체나 기능 구상·구현은 승인한 것이 아니다.

## 원칙을 설명하는 단위

`사용자 목적 → 현실의 마찰 → 맡길 책임 → 제품의 처리 방식 → 사용자에게 남는 행동 → 다음 단계의 가치 → 확인 방법`

브랜드의 표현을 그대로 개발 명령으로 바꾸지 않는다. 공식 자료에서 실제로 확인한 처리 방식과 후기에서 느낀 가치·불편을 먼저 나눈다. 그중 우리 사용자의 문제에도 해당하는 책임을 골라 구체적인 행동으로 옮긴다. 동일한 기계 기술이나 외형을 복제할 필요는 없다.

| 반드시 답할 것 | 설명이 부족한 문장 | 작업으로 연결되는 설명 |
| --- | --- | --- |
| 무엇을 덜 챙기는가? | 알아서 한다 | 질문 전마다 준비 여부를 확인하고 초기화 버튼을 누르는 일을 줄인다. |
| 제품이 무엇을 맡는가? | 보이지 않게 노력한다 | 기존 런타임을 재사용하고, 지원되는 워커 복구를 처리하며, 실패한 준비를 완료로 표시하지 않는다. |
| 왜 단계를 연결하는가? | 시너지가 있다 | 읽은 본문과 출처를 답변에 함께 전달해, 근거 확인을 위해 같은 문서를 다시 찾지 않게 한다. |
| 언제 사용자가 결정하는가? | 매우 심플하다 | 결과와 전송 범위를 바꾸는 선택은 사용자에게 남기고, 이미 정한 조건을 내부 단계마다 다시 묻지 않는다. |
| 무엇으로 맞다고 판단하는가? | 고급스럽다 | 지정 자료를 이용한 질문에서 수동 준비가 어디에 필요한지, 실패 후 입력이 살아 있는지, 출처가 실제 원문으로 이어지는지 확인한다. |

## A. P01의 중간 설명 · 질문부터 근거 확인까지 조율

**자동화에 관한 승인 조건:** 아래 사용자 행동은 예시 상황이며 고정된 수작업 분담이 아니다. 목적 표현·자료 선택·결과 검토도 기존 의도·맥락·설정·권한으로 자동 처리할 수 있는지 먼저 본다. 사용자가 해야 하는 일을 미리 고정하지 않고, 제품이 처리할 근거가 부족하거나 결정이 꼭 필요한 지점만 관여 대상으로 남긴다. 최소한의 관여로 전체 흐름이 움직이는 수준을 지향하되 구체적인 기능 idealisation은 이번 범위에서 제외한다.

**사용자 목적:** 선택한 자료로 두 설명을 비교하고 어느 주장에 근거가 있는지 판단하려 한다.

**현실의 마찰:** 질문은 하나인데 사용자가 준비 상태 확인, 검색 실행, 원문 읽기, 답변에 붙이기, 출처 다시 찾기를 별개 작업으로 관리하면 도구를 운영하는 일이 본래 조사보다 앞선다. 각 기능이 성공해도 전달이 끊기면 비교 결과를 쓰기 어렵다.

**참조 사례의 처리 방식:** Ghost는 전방 노면 감지·서스펜션·변속을 조율해 주행 경험에 연결한다(RR01). iCloud 발표는 기기마다 정보를 다시 옮기는 일을 앱과 서비스의 전달로 맡는다(AP05). 공통으로 참고하는 것은 사용자가 목적을 정한 뒤 하위 처리를 매번 중계하지 않도록 책임을 묶는 방식이다. 승차감이나 동기화 기술을 그대로 검색에 복제한다는 뜻은 아니다.

**우리 제품이 맡을 책임의 후보:** 질문과 지정 범위를 한 작업의 조건으로 유지하고, 그 안에서 자료 확보·원문 확인·답변 구성·출처 연결을 이어 간다. 준비를 시작하는 것과 근거를 확보한 것을 구분하며, 검색 후보를 읽은 원문처럼 사용하지 않는다.

| 상황 | 제품의 동작 후보 | 사용자 관여가 필요해질 수 있는 지점 | 다음 단계에 남기는 것 |
| --- | --- | --- | --- |
| 질문 전송 | 설정된 경로에서 필요한 준비를 확인·재사용하고 범위에 맞는 자료를 확보한다. | 목적·자료 범위·필요한 권한 결정 | 질문, 선택 범위, 확보한 자료의 상태 |
| 후보를 발견함 | 필요한 원문을 읽고 후보와 실제 확인한 출처를 구분한다. | 중요한 범위 변경이 있을 때만 결정 | 본문·출처·확인 상태 |
| 비교 답변 생성 | 확인한 근거를 주장과 연결하고 충돌·부족한 자료를 구분한다. | 내용 판단 | 비교 결과와 검토 가능한 출처 |
| 근거 확인 | 답변의 출처에서 실제 원문으로 이동할 경로를 제공한다. | 근거 검토 | 이어서 질문할 맥락 |
| 준비 실패 | 입력을 보존하고 무엇을 진행하지 못했는지, 가능한 다음 행동을 알린다. | 재시도 또는 조건이 달라지는 대안 선택 | 원래 목적과 다시 시작할 입력 |

**구체적인 결정:** 일상 전송 전에 모든 엔진별 실행 버튼을 필수로 누르게 하는 변경은 이 후보와 맞지 않는다. 준비 실패 시 전체 초기화만 제공하는 변경도, 더 작은 복구로 충분한지 먼저 따져야 한다. 이미 제공한 자료를 답변에 쓰기 위해 사용자가 다시 복사하도록 만드는 변경은 기능 사이의 책임을 사용자에게 되돌린다.

**현재 구현에서 확인한 연결 지점:** [main.ts](../../main.ts)의 `prepareRagForChat()`는 필요한 런타임 초기화와 닫힌 BM25 워커 복구를 호출한다. [view.ts](../../src/chat/view.ts)의 `buildPromptContext()`는 질문·기존 조건으로 자료 맥락을 준비하며, `handleSend()`의 준비 실패 경로에는 제출 초안 복원이 있다. [tool-execution.ts](../../src/chat/tool-execution.ts)의 `collectToolCitations()`는 출처를 ID로 모으고 원문 확인 상태로 갱신한다. [관련 테스트](../../src/chat/tool-execution.test.ts)는 후보에서 확인된 출처로 갱신하는 계약을 다룬다.

**아직 입증하지 않은 것:** 코드를 읽어 연결 지점은 확인했지만 실제 모델이 모든 질문에서 적절한 자료를 찾아 비교하는 품질, 전체 경로의 조작 수, 최신 원문으로의 정확한 이동을 이번 작업에서 실행 검증하지 않았다. 새로 구현이 필요한 범위는 해당 작업 때 호출부·화면·실제 동작으로 확인한다.

**수동 확인 시나리오 후보:** 볼트와 독립적으로 만든 두 합성 문서에 공통 주장과 서로 다른 주장을 넣는다. 동일 범위에서 질문하고, 자료 준비부터 근거 확인까지 별도 수동 중계가 어디에 필요한지 기록한다. 준비 실패를 별도로 재현해 입력 보존과 복구 행동을 확인한다. 출처가 있다는 사실만으로 답변 정확성에 합격을 주지 않는다.

**조건을 반영한 승인 문장:** 제품은 사용자의 의도와 기존 맥락·설정·권한을 바탕으로 자동화할 수 있는 판단과 작업을 최대한 맡아, 최소한의 관여로 목적을 이루게 한다. 목적 표현·자료 선택·결과 검토도 고정된 수작업으로 남기지 않는다. 제품이 처리할 근거가 부족하거나 사용자의 결정이 반드시 필요한 지점에서만 관여를 요청한다. 준비부터 결과 활용까지 맥락과 근거를 연결하고 실패 시 기존 작업을 보존한다.

## B. 보이지 않는 노력 · 바뀐 원문을 잘못 연결하지 않기

- **목적과 마찰:** 사용자가 근거를 믿고 비교하려는데 읽는 도중 문서가 바뀌면 본문·수정 상태가 섞일 수 있다. 사용자가 매번 수정 시각을 대조하는 것은 조사 업무가 아니다.
- **참조의 중간 기제:** Ghost의 주행 제어 조율(RR01)은 사용자가 매번 하위 처리를 감독하지 않게 제품이 조율하는 사례다. 몽블랑의 사용자 지정 참조 의미는 엘레강스함과 사용성이며 이 내부 처리 원칙의 근거로 확장하지 않는다.
- **맡길 책임과 동작 후보:** 제품이 원문과 상태의 일관성을 확인하고, 읽는 중 바뀐 본문을 새 상태의 근거로 확정하지 않는다. 불완전한 자료를 확실한 결과로 내보내지 않는다.
- **현재 지점:** [source-snapshot.ts](../../src/rag/source-snapshot.ts)는 읽기 전 상태를 보존하고 Rust의 revision 판정에 맞지 않으면 snapshot을 반환하지 않는다. [source-validation.ts](../../src/chat/source-validation.ts)는 출처 확인과 경고 계획을 Rust에 요청한다.
- **왜 시너지인가:** 사용자가 원문 상태를 수동 대조하지 않아도 이후 답변과 출처 검토가 같은 자료에 기반하도록 내부 연결을 지탱한다.
- **확인 방법 후보:** 읽기 중 변경·이동된 합성 원문이 잘못된 최신 근거로 저장되지 않는지, 그 경우 사용자에게 완료처럼 표시하지 않는지 확인한다. 기존 테스트를 읽은 사실은 이 전체 시나리오의 실행 성공과 구분한다.

## C. 매우 심플함 · 정상 준비는 조용히, 판단이 필요하면 분명히

- **목적과 마찰:** 질문하려는 사용자가 정상 준비 상태 알림을 매번 해석해야 하거나, 반대로 막힌 이유를 찾지 못하면 주의가 목적에서 시스템으로 이동한다.
- **참조의 중간 기제:** Naim의 다이얼과 근접 감지 표시(AS07), 당시 애플의 알림 정리(AP06)는 사용자가 필요한 조작·정보에 접근하게 하는 다른 방식이다. 표시를 그대로 복제하는 근거는 아니다.
- **동작 후보:** 정상 준비가 끝나면 반복적인 준비 안내를 물리고, 전송을 막는 조건이 있으면 현재 위치에서 이유와 해결 행동을 제공한다. 진단 상세는 실제 문제 해결에 필요할 때 찾을 수 있게 한다.
- **현재 지점:** [view.ts](../../src/chat/view.ts)의 `renderChatReadiness()`는 ready 상태에서 준비 영역을 숨기고 준비 snapshot으로 전송 가능 여부를 반영한다. [chat-ux-fixtures.test.ts](../../src/chat/chat-ux-fixtures.test.ts)에 구조 계약이 있다.
- **문구의 이유:** 문구는 “제품이 준비를 많이 한다”는 인상을 주려고 쓰지 않는다. 지금 전송할 수 있는지, 할 수 없다면 무엇이 필요한지 판단하게 하려고 쓴다.
- **확인 방법 후보:** 정상·미설정·준비 실패의 각 상태에서 필요한 선택을 설명할 수 있는지 실제 화면으로 확인한다. 안내를 숨긴 횟수가 아니라 사용자가 다음 행동을 알 수 있는지가 기준이다.

## D. "알아서" · 반복 질문 없이 복구하되 조건 변경은 선택으로

- **목적과 마찰:** 일시적인 응답 실패 뒤 같은 배경을 다시 입력하거나 무슨 조건이 바뀌었는지 모른 채 재시도하면 이전 작업의 가치가 사라진다.
- **참조의 중간 기제:** Miele AutoDos(AS15–AS18)는 반복 준비를 맡지만 소모품과 관리가 남는다. 자동화의 이점은 제거한 업무와 새로 생긴 업무를 함께 보아야 한다. AirPods의 원치 않는 전환(AS04)은 편의를 위해 작업 대상을 바꾸면 관리 부담이 돌아올 수 있음을 보여 준다.
- **동작 후보:** 원래 목적·입력을 활용한 재시도를 제공한다. 제공자 변경·자료 맥락 없이 보내기처럼 결과나 전송 조건을 바꾸는 대안은 사용자가 선택하게 한다. 이 구분을 버튼 이름과 실제 호출에 일치시킨다.
- **현재 지점:** [chat-error-actions.ts](../../src/chat/chat-error-actions.ts)는 오류별 복구 행동을 만들고, [view.ts](../../src/chat/view.ts)의 `handleChatRecoveryAction()`은 재생성·제공자 변경·RAG 없이 보내기를 서로 다른 동작으로 처리한다. 재생성이 동일 원문 snapshot을 그대로 재사용하는지까지 이번 읽기로 확정하지 않았다.
- **확인 방법 후보:** 실패 전후의 목적·자료 범위·선택한 조건을 비교하고, 각 대안이 어떤 조건을 바꿨는지 확인한다. 재시도 버튼이 있다는 사실만으로 맥락 보존에 합격을 주지 않는다.

## E. README·영상 · 심플함을 주장하기 전에 흐름을 보여 주기

- **목적과 마찰:** 처음 보는 사람이 기술 이름만 읽으면 자신이 무엇을 시작하고 어디까지 끝낼 수 있는지 알기 어렵다. “모두 자동” 같은 설명은 준비·제약을 만나면 기대를 깨뜨린다.
- **참조의 중간 기제:** 당시 애플의 촬영→편집, 앱→기기 전달 설명(AP02·AP05)은 기능을 목적 안에서 연결한다. 초기 HomePod의 서비스 제약(AS06)은 한 단계의 완성도가 전체 목적의 완성을 보장하지 않는 사례다.
- **문장 후보의 구조:** 대상 사용자의 작업 → 자료를 가져오는 방법 → 결과에서 확인할 근거 → 다음 활용 → 필요한 조건. 실제로 확인하지 않은 연결은 약속하지 않는다.
- **구체적인 단어 판단:** “자동”을 쓴다면 무엇을 자동 처리하는지와 남아 있는 선택을 붙인다. “무료”는 플러그인 제공과 외부 제공자 비용을 구분한다. 단어를 지웠을 때 조건이 더 모호해지면 짧아졌다는 이유만으로 채택하지 않는다.
- **확인 방법 후보:** 각 약속을 현재 구현의 사용 경로에 연결하고 실제 시연에서 전후 단계를 확인한다. README·영상·홍보 문구 자체는 이번 작업에서 수정하지 않았다.

## 나머지 후보에도 필요한 중간 설명

아래는 15개 후보 모두의 목적·마찰·처리·증거를 연결한 작업용 요약이다. P01은 사용자 역할의 자동화를 포함하는 조건부 승인, P02는 기본 품질 조건 승인, P03은 P01의 중복 적용 설명이다. P04·P05는 승인 원칙, P06은 P01의 중복 적용 설명이며 P07은 중복 독립 철학에서 제외했고 P08은 기존 계약이다. P09는 승인 원칙이며 나머지 초기 후보는 선행 기준에 포함되는 적용 설명으로 정리했다. 개별 후보의 근거·반례는 [후보 상세](candidates.md)에 있다. 구현 설계·통과 임계값·현재 합격 판정은 아니다.

P09는 사용자의 채택 의사로 철학의 방향이 확정됐다. 실제로 사용 만족이 생기는지는 코드 계약만으로 입증할 수 없으며 해당 작업의 관찰과 사용자 경험으로 확인한다. 어떤 후보도 “고급 브랜드가 한다”는 이유만으로 개발 우선순위나 기능을 정당화하지 않는다.

철학 검사(`philosophy_reviewer` 서브에이전트)는 자동화하지 않는다. 사용자가 범위를 지정해 요청할 때만 수동으로 한다. 이 문서 작성 중에는 위 시나리오나 철학 검토를 실행하지 않았다.
