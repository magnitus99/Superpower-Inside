# 철학을 작업물에 적용하는 구체 예시

**설명을 위한 가상 적용 예시다.** 원칙의 승인·포함·제외 상태는 [결정 기록](../decisions/status.json), 현재 기준은 [제품 철학](../../product-philosophy.md)을 따른다. 현재 구현의 오류를 진단한 결과나 새 기능 구현 지시가 아니다. 예시는 실제 볼트와 무관한 합성 자료 A·B를 사용한다. 작업 범위·성능 임계값·승인 계약을 바꾸려면 별도 구현 판단과 검증이 필요하다.

## J01: 두 자료의 차이를 묻고 근거를 확인한다

- 상황: 사용자는 두 문서 A·B를 참조하고 서로 다른 주장을 비교해 달라고 요청한다.
- 후보 가치: P01·P05·P06·P10. 기능별 제어 없이 비교를 끝내고 원문에서 확인한다.
- 기대 결과: 관련 내용을 읽어 비교하고, 각 주장에 근거가 있으면 원문 위치로 돌아갈 수 있다. 읽지 못한 자료나 한도 때문에 빠진 부분을 읽었다고 표현하지 않는다.
- 불합격 예: 비교 답변은 생성됐으나 근거 버튼이 다른 위치를 연다. 또는 사용자가 문서별 출처를 다시 찾아 붙여야 한다.

| 영역 | 적용 후보 | 확인할 실제 증거 |
| --- | --- | --- |
| Rust/WASM | 추출·검색 결과에 필요한 원문 식별과 위치를 유지하고 자료의 서로 다른 주장·언어를 특정 정답으로 하드코딩하지 않는다 | 합성 입력의 위치 매핑·왕복 계약, 원문 변경 조건의 결과 |
| TypeScript | 선택 범위와 실패를 정확히 전달하고 최신 작업의 결과만 표시한다. 출처를 열 때 전달받은 위치를 사용한다 | 실제 호출 흐름·최신 작업 전환·출처 열기와 오류 상태 |
| 사용자 문구 | “비교 중”, “읽지 못한 자료” 등 실제 작업·한계를 뜻하는 문구가 필요한 위치에 있어야 한다 | 상태와 실제 읽기 범위의 일치, 한영 의미 일치 |
| README | “비교”가 무엇을 제공하고 어떤 근거로 돌아갈 수 있는지 설명한다 | 문장별 구현 근거·지원 조건 |
| 영상·마케팅 | 질문→비교→근거 확인의 실제 연결을 보여 준다 | 시연에서 누락된 초기 준비·시간 편집·모의 처리의 구분 |

계산을 TS로 옮기거나 WASM 실패를 다른 계산으로 숨기는 요구가 아니다. 구현 경계는 기존 `AGENTS.md`를 따른다.

## J02: 답변을 내 작업으로 옮긴다

- 상황: 사용자가 답변의 비교 결과를 노트나 개요에 활용하려 한다.
- 후보 가치: P06·P08·P13. 결과를 옮겨도 다시 판단할 근거가 남는다.
- 기대 결과: 내보내기·복사·저장이 제공되는 경로에서 출처와 문맥이 어떤 형태로 남는지 알 수 있다. 보존하지 못하는 정보는 그 제한을 설명한다.
- 불합격 예: 화면에는 출처가 있으나 저장된 결과에는 근거가 사라진다. 또는 원문이 바뀌었는데 오래된 결과를 현재 검증 완료처럼 표시한다.
- 확인할 증거: 결과 활용 전후에 내용·출처·원문 버전 의미를 비교한다. 다시 열었을 때 사용자가 원문을 찾을 수 있는지 관찰한다. 현재 기능의 계약 이상을 제품 설명에서 약속하지 않는다.

이때 “모든 출력을 반드시 영구 저장”하는 기능을 새로 도입하라는 뜻은 아니다. 기존 활용 경로가 전달하는 의미를 먼저 검토한다.

## J03: 준비가 오래 걸리거나 연결이 실패한다

- 상황: 처음 준비한 자료의 처리가 길어지거나 제공자·외부 도구가 응답하지 않는다.
- 후보 가치: P02·P03·P04·P11. 사용자의 의도가 관리 업무로 바뀌지 않게 한다.
- 기대 결과: 지금 가능한 행동과 기다려야 하는 행동을 구분한다. 처리 중이라는 피드백, 실제 중단 범위, 실패한 부분과 복구 행동을 알 수 있다. 입력과 사용자가 보고 있던 결과를 잃지 않는다.
- 불합격 예: 완료 전 성공 표시, 상태 없는 버튼, 같은 요청의 중복 실행, 모든 자료를 지워야만 재시도하는 경로.
- 확인할 증거: 합성 실패·취소·중복 조작·재시도 상황에서 호출 횟수와 자료 손실을 확인한다. 원격 추론을 실제로 취소할 수 없다면 그 능력이 있는 것처럼 표현하지 않는다.

시간 기준은 처리 종류와 검증 기기·자료를 정한 뒤 측정한다. 웹 반응 시간 지침을 긴 추론이나 OCR의 완료 시간에 그대로 적용하지 않는다.

## J04: 같은 보기 조작을 반복한다

- 상황: 사용자가 답변의 출처나 작업 기록을 여러 번 펼치고 접거나, 질문을 고친 뒤 이전 결과를 확인한다.
- 후보 가치: P05·P10·P12. 작은 제어가 안정되고 예상 가능하다.
- 기대 결과: 보기 조작의 이름과 실제 효과가 일치한다. 단순한 펼침·접힘이 자료·연결 상태를 바꾸려면 명시적인 이유와 동작 계약이 있어야 한다. 늦게 도착한 이전 요청이 새 요청의 결과를 덮지 않는다.
- 불합격 예: 보기만 바꿨는데 불필요한 재연결이나 전체 처리가 시작되고 입력 또는 현재 위치가 초기화된다.
- 확인할 증거: 클릭 이벤트부터 저장·재연결·처리 호출까지 추적한다. 반복 동작·오류·키보드·좁은 폭에서는 기존 화면 검수 계약을 따른다.

버튼 색이나 배치의 취향을 철학 판단으로 대신하지 않는다. 화면 규칙은 `design.md`를 사용한다.

## J05: 숙련 사용자의 방식과 애착을 고려한다

- 상황: 사용자가 익숙한 자료 범위·언어·프롬프트를 쓰며 의미 있는 결과를 축적한다.
- 후보 가치: P07·P09·P14. 주도권과 개인 적합성을 보존하면서 기본 흐름도 완결한다.
- 기대 결과: 사용자가 선택한 작업 방식을 존중한다. 기본 작업을 위해 깊은 설정을 강제하지 않고 필요할 때 접근할 수 있게 한다. 애착을 만든다는 이유로 강제 애니메이션·축하·명품 문구를 추가하지 않는다.
- 불합격 예: 개인화 메뉴만 늘리고 기본 경로는 복잡하게 만들거나, 사용자가 익숙하게 쓰던 선택을 이유 없이 바꾼다.
- 확인할 증거: 다른 언어·자료·숙련도의 사용 흐름을 관찰한다. 성취감·애착은 조사자의 느낌 대신 사용자가 실제로 하는 말과 반복 사용의 이유로 확인한다.

## 예시를 실제 검토로 옮길 때

`사용 상황 → 필요한 가치(P-ID) → 실제 동작 → 출처와 적용 한계 → 관찰할 증거`

[수동 검토 양식](../review/manual-review.md)은 별도 요청이 있을 때만 사용한다. 이 예시를 읽는 것만으로 실제 검토를 시작하지 않는다.

문구 하나도 어떤 상태에서 어떤 판단을 돕는지 연결한다. 버튼 하나도 실제 효과와 부작용을 확인한다. README의 단어 하나도 적용 조건을 확인한다. 영상의 장면 하나도 앞뒤 단계와 실제 연결을 확인한다. Rust의 결과 필드 하나도 다음 단계의 의미를 보존하는지 확인한다.

가상 예시를 확정 기능·새 조건으로 확대하지 않는다. 기존 승인 문장과 기능·안전 계약을 유지하며 새로운 방향이나 조건이 필요하면 그 범위만 사용자와 합의한다.
