# P02 재검토 · 준비와 검색 품질

**현재 상태: 수정된 문장을 기본 품질 조건으로 승인.** 최종 승인 문장은 “제품은 사용자의 수고를 줄이되, 그 대가로 결과의 충실도를 낮추지 않는다. 충분히 처리하지 못한 부분은 완료한 것처럼 제시하지 않는다.”다. 기존 P01의 승인 문장과 조건은 변경하지 않았고, 아래 P01 통합 제안과 준비 관련 설명은 재검토 당시의 기록으로 보존한다.

**이전 검토 상태: 승인 대기·수정 요청 기록.** 사용자는 준비의 실제 범위와 이 원칙의 채택 효과, BM25 의존 여부를 물었다. 이것은 P02의 승인이나 검색 전략 변경 요청이 아니다.

## 현재 구현에서 확인한 사실

- [main.ts](../../main.ts)의 `initRAGRuntime()`는 BM25가 켜져 있을 때 임베딩 제공자·벡터 저장소가 없는 검색 엔진을 먼저 만들고 BM25를 백그라운드로 로드한다. 임베딩 모델이 없을 때에도 키워드 검색용 이벤트를 등록하는 경로가 있다.
- 같은 파일의 `finishBM25BackgroundLoad()`는 저장된 색인을 로드하고 문서 범위·토크나이저·revision 상태 등에 따라 재구축한다. BM25는 준비가 전혀 필요 없는 검색이 아니다.
- [query.ts](../../src/rag/query.ts)의 `query()`는 질문 임베딩 실패를 기록하고 나머지 검색 경로를 이어 간다. [retrieval-pipeline.ts](../../src/rag/retrieval-pipeline.ts)는 query vector가 없으면 vector·ANN 경로를 건너뛰고, BM25는 색인이 준비됐을 때만 후보를 반환한다.
- [query.test.ts](../../src/rag/query.test.ts)에 벡터 없는 BM25 결과를 유지하는 계약이 있다. 이번 검토에서는 테스트를 실행하거나 실제 답변 품질을 평가하지 않았다.

임베딩 생성·갱신은 사용자가 체감할 수 있는 주요 준비다. 이와 별도로 로컬 색인 로드·재구축·런타임 초기화도 있지만, 내부 과정의 종류가 많다는 사실만으로 독립 철학 원칙을 정당화하지 않는다.

## 앞선 제안의 문제

“이미 가능한 행동을 제공한다”는 표현만으로는 임베딩 준비 중 어떤 결과를 제공해도 되는지 결정할 수 없다. 즉시 응답해도 요청한 자료를 충분히 확보하지 못했다면 원래 목적을 완성한 것이 아니다. BM25 경로의 존재는 임베딩과 같은 품질·범위의 결과를 보장하지 않는다.

P02 채택은 BM25만 쓰기, 임베딩 없이 모든 질문 처리하기, 품질보다 먼저 답변하기에 대한 승인이 아니다. 기존 검색 전략이나 기본값도 바꾸지 않는다.

## 제안: 독립 원칙보다 P01의 조건으로 통합

**통합 후보 문장:** 제품은 필요한 준비를 재사용하고 관리 부담을 맡되, 빠르게 응답하기 위해 필요한 근거를 희생하지 않는다. 대체 경로의 결과가 요청을 충족하지 못하면 부족한 범위를 밝히고 완료로 표현하지 않는다. 준비·실패 때문에 사용자가 목적과 입력을 다시 만들게 하지 않는다.

이 문장은 사용자 승인 전이다. P01에 실제로 추가하거나 P02를 통합 완료로 처리하지 않았다. 구체적인 자동화 기능 구상·구현은 이번 범위가 아니다.

## 채택하면 무엇을 판단하는가

- 임베딩이 필요 없는 상황이나 이미 준비된 자료에 대해 불필요하게 전체 준비를 반복시키는가?
- 대체 경로가 있다는 이유만으로 확보하지 못한 자료까지 검토한 것처럼 답하는가?
- 실패·대기 이후 원래 질문과 작업을 다시 입력하게 하는가?

첫 질문은 준비 관리의 책임, 둘째는 결과의 충실도, 셋째는 기존 작업 보존의 책임이다. 실제 변경의 필요성은 해당 요청의 구현·호출부·동작에서 확인한다. 이 문서만으로 새 대기 정책이나 검색 fallback을 구현하지 않는다.
